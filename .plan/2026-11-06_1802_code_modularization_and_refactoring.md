## 1. 핵심 문제점 분석

1. **파싱·선택과목 매핑 엔진의 이중 관리 (약 2,250줄 완전 중복)**
   - `Code.gs`의 파서/선택과목 함수(`parseSheetAutoLayout_`, `crossEnrichTimetables_`, `applyElectiveClassroomMapping_` 등)와 `index.html`의 클라이언트 함수(`*Client_`)가 동일한 로직으로 중복 작성되어 있어, 규칙 수정 시 두 파일을 항상 동시에 고쳐야 하고 누락 시 서버-클라이언트 결과 불일치가 발생할 위험이 큽니다.
2. **단일 파일(`index.html` 9,930줄) 비대화로 인한 탐색·유지보수 비용 증가**
   - 스타일시트(CSS), 모달 마크업(HTML), 문서 내보내기(XLSX/HWPX XML 생성기), BIFF8 엑셀 디코더, 시간표 UI 로직이 한 파일에 모여 있어 코드 탐색과 수정 속도가 저하됩니다.

## 2. Google Apps Script(GAS) 환경에 최적화된 효율적 코드 관리 방안

GAS 환경의 특성을 활용하면 **초기 로딩 속도(0ms 캐시 주입, 추가 네트워크 요청 0회)를 100% 그대로 유지**하면서도 파일 크기와 중복 코드를 대폭 줄일 수 있습니다.

### 방안 A. 서버(`Code.gs`) 역할별 파일 분리 (성능 오버헤드 0%)
GAS 프로젝트 내 모든 `.gs` 파일은 실행 시 단일 전역 스코프로 자동 병합됩니다. 따라서 `Code.gs`(3,480줄)를 아래 4개 파일로 분리하면 각 파일이 600~1,200줄 내외로 깔끔하게 관리됩니다.

| 분리 파일명 | 담당 역할 및 주요 함수 | 예상 줄 수 |
| :--- | :--- | :---: |
| **`Code.gs`** | 웹앱 진입점(`doGet`, `include`), 멀티청크 `CacheService` 캐시 읽기/쓰기, 초기 페이로드 반환 | ~550줄 |
| **`Parser.gs`** | 주간/학급시간표 4대 레이아웃 파서(`tryParseHorizontalMatrix_`, `tryParseFiveDayBlocks_` 등) 및 교차 보완(`crossEnrichTimetables_`) | ~1,400줄 |
| **`Elective.gs`** | 2·3학년 선택과목 시트 파싱 및 실제 강의실(`301~309호`, `401~409호`, `211호`, `315호`, `416호`, `정보실`) 매핑 엔진 | ~650줄 |
| **`ProjectService.gs`** | 학기별 시트 세트(Project) 생성/삭제/업로드, 교사 그룹(`교사그룹` 시트) 저장/조회 | ~800줄 |

### 방안 B. 프론트엔드(`index.html`) 서버사이드 템플릿 분할 (`<?!= include(...) ?>`)
GAS `HtmlService`의 `include()` 헬퍼 함수를 사용하면, 개발·관리 시에는 역할별 `.html` 파일로 나누어 편집하고, 사용자 접속 시에는 서버에서 1개의 HTML로 합쳐서 내려주므로 **브라우저 추가 HTTP 요청 없이 기존과 100% 동일한 렌더링 속도**를 유지합니다.

| 분리 파일명 | 담당 역할 | 예상 줄 수 |
| :--- | :--- | :---: |
| **`index.html`** | 메인 HTML 레이아웃 뼈대 및 모달 마크업 + 템플릿 인클루드 호출 | ~500줄 |
| **`Stylesheet.html`** | `<style>` 전체 디자인 토큰, 시간표 테이블, 모달, 반응형/인쇄 CSS | ~2,150줄 |

| **`ClientApp.html`** | 상태 관리(`state`), 초성 검색, 시간표/공강/수업교사 렌더링, 시트 세트 모달 제어 | ~3,000줄 |

### 방안 C. 서버-클라이언트 파서 중복(~2,250줄) 제거 (단일 코어 엔진 공유)
가장 큰 비중을 차지하는 **서버(`Code.gs`) ↔ 클라이언트(`index.html`) 파서 및 선택과목 매핑 로직 중복(약 2,250줄)**을 해결하는 두 가지 방법입니다.

1. **방법 C-1 (권장 · 즉시 체감 효과 최대): 업로드 시 서버 파서 단일화**
   - 현재 브라우저(`index.html`)에 2,250줄의 파서(`*Client_`)가 들어 있는 유일한 이유는 **'시트 세트 관리' 모달에서 엑셀 파일 업로드 시 서버 응답 전에 브라우저에서 먼저 파싱하기 때문**입니다.
   - 하지만 엑셀 파일을 2D 배열(`rows`)로 읽는 작업(`ClientExcelReader`)만 브라우저에서 수행하고, 시간표 구조 파싱 및 선택과목 매핑은 이미 서버의 `uploadProjectSheets()`(`Code.gs`)가 수행하여 완성된 JSON(`payload`)을 반환하고 있습니다!
   - 따라서 `uploadProjectSheets()`가 반환한 서버 파싱 결과를 그대로 화면에 적용하면, **`index.html` 내부의 중복 파서 코드 약 2,200줄(`parseSheetAutoLayoutClient_`, `crossEnrichTimetablesClient_`, `applyElectiveClassroomMappingClient_` 등)을 완전히 삭제**할 수 있습니다.
   - **효과**:
     - `index.html` 크기가 **9,930줄 → 약 7,700줄(약 23% 즉시 감소)**로 줄어듭니다.
     - 앞으로 시간표 파싱이나 선택과목 매핑 규칙을 수정할 때 **`Code.gs` 한 곳만 수정**하면 되어 유지보수 속도가 2배 빨라지고 서버-클라이언트 불일치 버그가 원천 차단됩니다.

2. **방법 C-2 (오프라인 단독 실행까지 유지 필요한 경우): 공통 파서 스크립트 자동 주입**
   - 서버 없이 로컬 파일만으로 동작하는 폴백 기능까지 유지해야 한다면, `Parser.gs`와 `Elective.gs`의 순수 JS 함수들을 `doGet` 시점에 `<script>`로 자동 주입하거나 별도 `SharedParser.html`로 분리하여 단일 소스로 관리할 수 있습니다.
